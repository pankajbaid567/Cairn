# V3: `docker compose up --wait` with a one-shot dependency

Resolved 27 Oct 2026 in task 4.1 with Docker Compose v2.40.3-desktop.1 (Docker Desktop 28.5.1).

## Result

`up --wait` works with a `service_completed_successfully` one-shot dependency. The sequential fallback in design §4 is not needed.

| Case | Setup | Outcome |
|---|---|---|
| A: one-shot with no dependents | The real stack: `docker compose --profile core up --wait` with `db` (healthcheck) and `db-init` (one-shot, `restart: "no"`, exits 0) | Exit 0. Compose printed `db-init Healthy` for the exited container; `ps -a` then showed `db-init exited 0` |
| B: long-running service that depends on the one-shot | Scratch project (not in the repo): `oneshot` exits 0 after 3 s, `longrun` has a healthcheck and `depends_on: oneshot: condition: service_completed_successfully` | Exit 0. `oneshot Exited`, then `longrun Started`, then `longrun Healthy` |
| C: the one-shot fails | Same scratch project with `oneshot` exiting 1 | Exit 1 with `service "oneshot" didn't complete successfully: exit 1`; `longrun` never started |

Case B is the shape the final stack has (api and worker depend on db-init, tasks 5.4 and 6.3). Case C shows `make up` fails loudly when bootstrap or a migration fails (Requirement 4.3).

## Consequences

- `make up` (task 8.1) can be a plain `docker compose --profile core up --wait`, with the failure output from design §4 (`ps` plus the last 50 log lines of the failing service) added on error.
- `make up-db` uses `up --wait --no-deps db`; `make db-init` uses `run --rm --build db-init`, which also gives the one-shot's output on the terminal.
- A second `up` re-runs `db-init` (it is a normal service with a stopped container). That is intended: bootstrap and migrate are idempotent.

The scratch project lived in a temporary directory and was removed after the run.

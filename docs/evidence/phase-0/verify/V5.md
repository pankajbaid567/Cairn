# V5: ParadeDB BM25 DDL, query syntax, `int[]` fields and EXPLAIN keys
Date: 27 Oct 2026. Resolved by task 14.2. Checked on the compose `db` service: `paradedb/paradedb:0.26.3-pg18` (digest in `docker-compose.yml`), PostgreSQL 18.6, `pg_search` 0.26.3, `pgvector` 0.8.6. Evidence: the S2 harness run on 20,000 rows × 384 dimensions, `docs/spikes/S2/2026-10-27-report.md` and `-results.json` (all raw plans), plus 2,000-row probes in throwaway `cairn_test_<hex>` databases.
| Item | Result |
|---|---|
| BM25 DDL | `CREATE INDEX chunks_bm25_idx ON s2.chunks USING bm25 (id, body, acl) WITH (key_field = 'id')`. `pg_indexes` shows it back as `WITH (key_field=id)`. The key field must be in the column list. No `paradedb.create_bm25` call is needed in 0.26 |
| `int[]` in the index | **Accepted.** `acl int[]` indexes without a fallback, so the Requirement 16.7 path (index over `id, body` only) did not trigger. The fallback is still coded and unit-tested with a fake executor |
| Match syntax | `body ||| 't9_0 t9_1'` is match-any over the analyzed terms (`&&&` would be match-all). The score is `pdb.score(id)`, ordered with `ORDER BY pdb.score(id) DESC LIMIT n` |
| ACL as an index predicate | `acl @@@ pdb.term_set(ARRAY[1000])` works on the `int[]` field and is pushed into the index: the Tantivy query holds `{"term_set":{"field":"acl","terms":[1000]}}`. The plain operator `acl && '{1000}'::int[]` is **not** translated; ParadeDB keeps it as a heap filter. The harness measures `&&` because that is the RLS policy shape |
| Roles | `cairn_app` runs `|||` and `pdb.score()` with no grant beyond `USAGE` on the spike schema and `SELECT` on the table. Bootstrap's `USAGE` on schema `paradedb` is enough; nothing extra was needed for schema `pdb` |
| Plan node | `"Node Type": "Custom Scan"`, `"Custom Plan Provider": "ParadeDB Base Scan"`, `"Index": "<bm25 index>"` (not `Index Name`), `"Table"`, `"Exec Method"` (for example `TopKScanExecState`), `"Heap Fetches"`, `"Segment Count"`, `"Buffer Hits"` |
| Filter keys | `"Tantivy Query"` is a **string** holding JSON. A predicate it cannot push appears as `heap_filter` and `recheck_filters[].heap_filter` (text of the predicate). A pushed predicate appears as a `term_set` (or other query) with `"field": "acl"`. Some ParadeDB keys have leading spaces (`"   TopK Order By"`, `"   TopK Limit"`), so a lookup must not assume trimmed names |
| GIN intersection | With a GIN index on `acl`, the custom scan lists `"Bitmap Intersection": "<gin index>"` and a child `Bitmap Index Scan` on the GIN index with an `Index Cond` on `acl`; `"Bitmap Rejected Docs"` counts candidates dropped by the intersection |
| pgvector keys | An HNSW scan is `Node Type = "Index Scan"` with `"Index Name"` = the HNSW index and `"Order By"`. Under RLS or with an explicit predicate the ACL appears as `"Filter"` on that node with `"Rows Removed by Filter"`, so HNSW is a post-filter. A GIN bitmap chosen by the planner shows as `Bitmap Heap Scan` plus `Sort`, with no HNSW index in the plan |
| Standard keys | `Plans` (children), `Actual Rows`, `Actual Loops`, `Rows Removed by Filter`, top-level `Execution Time` (ms). `Seq Scan` carries `Relation Name` and `Alias` |
## Hazards found
1. **Empty setting after `SET LOCAL`.** After a transaction that used `SET LOCAL cairn.principal_groups`, the connection keeps the setting as the empty string. The design policy `acl && current_setting('cairn.principal_groups', true)::int[]` then raises `malformed array literal: ""` instead of denying. A fresh connection reads NULL and denies. The harness policy wraps the setting in `nullif(…, '')`, so both cases return zero rows; the report has a "setting left from an earlier transaction" default-deny row for this. ADR-0004 and ADR-0006 should use the `nullif` form. This is a deviation from design §14 step 2.
2. **Plan reuse hides differences.** A statement with no parameters is planned once and the plan is reused. psycopg prepares a query text on its fifth execution (`prepare_threshold = 5`), after which a later run with another principal or `hnsw.iterative_scan` reuses the first plan. The first 20,000-row run showed this as recall 1.00 for HNSW plans that returned 4 rows. The S2 connections set `prepare_threshold=None`. The API's pool needs the same care wherever the principal or an HNSW setting changes between executions of the same text.
3. **Planner choices, not harness bugs.** At 20,000 rows the planner sometimes prefers the GIN bitmap plus sort over HNSW for the 1% and 5% principals. Recall there is 1.00 because that path is exact, so recall is only informative for plans that use the HNSW index.
## Findings at 20,000 rows (input to ADR-0006, not the decision)
- Default deny holds: zero rows with no setting, with `{}`, and with a stale setting; `SET row_security = off` raises `42501`; `cairn_owner` sees zero rows; the superuser sees all 20,000.
- BM25 uses the ParadeDB scan under RLS for every principal and iterative-scan value. The ACL runs as a GIN bitmap intersection plus a heap recheck, not inside the index. With RLS alone (no explicit predicate) the BM25 median is about 30 ms (11 to 74 ms); with the explicit literal predicate added it is about 1.3 ms (0.4 to 4.8 ms).
- HNSW under RLS uses the HNSW index with the ACL as a post-filter for the 5%, 20% and 50% principals. With `iterative_scan = off` and `ef_search = 40` it returns fewer than 10 rows (4 for p05, 8 for p20; recall 0.21 and 0.73); `strict_order` returns 10 with recall 1.00.
- No sequential scan on the spike table appeared in any plan.

# V2: DBOS Transact 3.3.0 schedule API, cron, logging, privileges and shutdown

Date: 27 Oct 2026. Resolved by task 6.1 by reading the installed package source
(`.venv/lib/python3.12/site-packages/dbos`, `dbos` 3.3.0, `croniter` 6.2.4, `sqlalchemy` 2.1.6).
Nothing here was run against a database; the points marked "unit-tested" have a test in
`apps/worker/tests/unit`, and the rest are read from source and must be seen once in the task 6.3
integration test.

| Item | Result |
|---|---|
| Schedule API | `DBOS.apply_schedules(list[ScheduleInput])` exists (`_dbos.py:3211`). It atomically creates **or replaces** schedules in one transaction (`upsert_schedule`), so calling it on every start is idempotent. `ScheduleInput` (exported from `dbos`) keys: `schedule_name`, `workflow_fn`, `schedule`, `context`, `automatic_backfill`, `cron_timezone`, `queue_name`. Also available: `create_schedule` (fails if the name exists), `list_schedules`, `delete_schedule`, `pause_schedule`, `resume_schedule`, `backfill_schedule`, `trigger_schedule` |
| When to call it | After `DBOS.launch()` (it reads `dbos._sys_db`, which exists only after launch) and not from inside a workflow. The workflow function must already be registered, which the `@DBOS.workflow()` decorator does at import time |
| Pickup latency | The scheduler is a polling loop (`dynamic_scheduler_loop`). Default `scheduler_polling_interval_sec` is 30 s, but during the first 60 s after launch it polls every 1 s, so a schedule applied right after launch starts within about a second. Each schedule gets its own thread |
| Workflow signature | `(scheduled_time: datetime, context: Any) -> None` (type `ScheduledWorkflow`). `scheduled_time` is timezone-aware (UTC unless `cron_timezone` is set). `context` is serialized into the schedule row and handed back on every run. The return type must be `None` for mypy to accept it as `workflow_fn` |
| Cron fields | **Six fields are accepted, seconds first**: `second minute hour day month weekday`. Five fields are `minute hour day month weekday`. DBOS validates with `croniter.is_valid(cron, second_at_beginning=True)`. Unit-tested with croniter: `*/30 * * * * *` at 12:00:10 fires 12:00:30; `*/5 * * * * *` at 12:00:10 fires 12:00:15; `5 * * * *` fires 12:05:00. Bad cron raises `DBOSException("Invalid cron schedule: ...")` from `apply_schedules`. Cairn's `heartbeat_cron` validator already requires 5 or 6 fields |
| Run identity | Workflow id is `sched-<schedule_name>-<fire time ISO>`; a run whose id already exists is not enqueued again, so two workers cannot double-fire a tick. Runs go on DBOS's internal queue. `schedule_name` is stored on the `workflow_status` row |
| Listing runs by schedule | `DBOS.list_workflows(schedule_name="cairn-heartbeat", status="SUCCESS", sort_desc=True, limit=...)` exists (`schedule_name: str | list[str]`). It returns `WorkflowStatus` objects, scoped by default to this application name (`cairn-worker`). Statuses: `ENQUEUED, PENDING, SUCCESS, ERROR, CANCELLED, MAX_RECOVERY_ATTEMPTS_EXCEEDED, DELAYED`. Task 6.3 can poll this, or query `dbos.workflow_status` directly as `cairn_dbos` |
| Passing the database URL | `DBOSConfig["system_database_url"]` is a string; there is no separate password field. Alternatives are `system_database_engine` (a ready SQLAlchemy engine, which also skips DBOS's pool, idle-timeout and `postgres`-database existence check) or the `DBOS_SYSTEM_DATABASE_URL` environment variable (only in the cloud/`dbos-config.yaml` path). Decision: the string, percent-encoded, built in memory at the last moment from `SecretStr`. DBOS itself only ever logs the URL with `render_as_string(hide_password=True)` (`_sys_db.py:686-695, 848`) and logs engine kwargs, which do not contain it. Cairn code never logs the config dict, the URL or the password. The liveness probe does not use a URL at all: it passes keyword arguments to `psycopg.connect` |
| Pool size | `sys_db_pool_size` overrides the default 20; Cairn sets 5. `max_overflow` is 0, `pool_timeout` 30 s, `connect_timeout` 10 s unless the URL has `connect_timeout=` |
| Privileges and extensions | **No `CREATE EXTENSION` anywhere** in DBOS's migrations (`_migration.py`); `gen_random_uuid()` is built into PostgreSQL 13+. Needed from `cairn_dbos`: CONNECT on `cairn_dbos`; CREATE on that database (to `CREATE SCHEMA dbos`, only when the schema is missing); ownership of schema `dbos` (the migrations create tables, plpgsql functions `enqueue_workflow`, `send_message`, `*_function` and triggers, and `NOTIFY` channels); `LISTEN`. Role `cairn_dbos` owns the database, so all of this holds. Because the role is not a superuser, bootstrap does not need to pre-create any extension for DBOS (design Verify V2 fallback not needed) |
| Extra connection at migrate time | With a URL (not a custom engine), `run_migrations` first connects to the **`postgres`** database to check that `cairn_dbos` exists, and only logs a warning "Could not connect to postgres database ... Continuing" if that fails. Bootstrap revokes PUBLIC CONNECT only on `cairn` and `cairn_dbos`, so the default PUBLIC grant on `postgres` still lets this succeed. Do not revoke it. A failure would be a warning, not an error |
| Migration locking | Session advisory lock 1234567890 for up to 30 s, then proceeds without the lock with a warning. `run_migrations=False` makes launch verify the schema instead and fail if it is missing or behind. Cairn uses `True` (design §8) |
| Logger propagation | **Not propagated by default.** `DBOS()` calls `init_logger()`, which, if the `dbos` logger has no handler, adds a plain-text `StreamHandler` and sets `propagate = False`. Records would bypass `configure_logging` and not be JSON. Fix, unit-tested: add a `logging.NullHandler()` to the `dbos` logger (and set `propagate = True`) before constructing `DBOS`; `init_logger` then leaves the logger alone and records flow to the root JSON handler with `logger = "dbos"`. `cairn_worker.app.prepare_dbos_logging()` does this. `DBOSConfig["log_level"]` sets the `dbos` logger level (Cairn passes `CAIRN_LOG_LEVEL`). DBOS adds `applicationID`, `applicationVersion`, `executorID` and, inside a workflow, `operationUUID` as record attributes through a filter on the `dbos` logger; the Cairn formatter emits them as extra fields |
| OTLP | `enable_otlp: False` makes DBOS skip its own OTLP logging and tracing (`disable_otlp`), so no `opentelemetry-instrumentation-logging` import is needed. Spans come from Cairn's tracer provider only. `trace.get_tracer(__name__)` at module level is a proxy that picks up the provider installed later by `configure_tracing` |
| Import warnings | `import dbos` is warning-free under `python -W error` (checked), so `filterwarnings = ["error"]` needs no exception in the worker tests |
| Shutdown | `DBOS.destroy(destroy_registry=False, workflow_completion_timeout_sec=0)` stops background threads, shuts the executor down without waiting (`wait=False, cancel_futures=True`), joins each background thread for up to 10 s, and disposes the engine. **DBOS installs no signal handlers** (no `signal`/`atexit` use in `_dbos.py`, `_core.py`), so the worker must handle SIGTERM and SIGINT itself. Normal case is well under 10 s (scheduler threads wake on their stop event; the scheduler join is capped at 5 s). Worst case is several 10 s joins, so Requirement 8.7 (10 s) needs a measurement in task 6.3 (`docker compose stop worker`; compose `stop_grace_period` default is 10 s) |
| Signal delivery caveat | A bare `Event.wait()` in the main thread did not wake when the signal was raised from another thread (the test hung): the kernel can deliver a process signal to any thread, and the interpreter only runs the Python handler when the main thread next executes bytecode. `wait_for_signal` therefore polls `Event.wait(0.25)` in a loop |
| Enqueue on a caller's transaction | **Possible only when the content tables and the DBOS system tables are in the same database.** DBOS 3.3.0's migrations define (and redefine, most recently in the code path I read, `get_dbos_migration_hundredthirteen`) a SQL function `dbos.enqueue_workflow(workflow_name, queue_name, positional_args, named_args, ..., workflow_id, deduplication_id, priority, delay_until_epoch_ms, ...)` that does a plain `INSERT INTO dbos.workflow_status` (and `send_message` for notifications). Calling it with `SELECT dbos.enqueue_workflow(...)` on the caller's own connection joins the caller's transaction, so the job exists if and only if the content write commits. The Python `DBOS.enqueue_workflow` / `Queue.enqueue` / `DBOSClient.enqueue` open their own system-database connection and cannot join a caller's transaction. DBOS also has "datasources" (`SQLAlchemyDatasource`, `_datasource_postgres.py`) that run workflow steps as transactions in an application database with checkpoints, a different mechanism (step transactions, not enqueue). With PD-07 (separate `cairn_dbos` database) the SQL function is unreachable from a `cairn` connection, since PostgreSQL has no cross-database queries. Options for ADR-0002 and tasks 3.4 and 3.5, none taken now: (a) keep the separate database and use a transactional outbox table in `cairn` that the worker drains into DBOS; (b) put schema `dbos` in database `cairn` (`dbos_system_schema`/URL pointing at `cairn`), owned by a DBOS role, grant `cairn_app` EXECUTE on `dbos.enqueue_workflow` only (`DBOS.migrate(url, application_role=...)` grants broader rights, so write narrower grants by hand), and keep FORCE RLS on content tables. (b) weakens the "DBOS tables away from content" reason in PD-07 |

## Decisions that follow

- `cairn_worker.app.dbos_config` builds `system_database_url` from `WorkerSettings`; role `cairn_dbos` and database `cairn_dbos` (setting `CAIRN_DBOS_DB_NAME`); pool 5; `run_migrations: True`; `enable_otlp: False`; `log_level` from settings.
- `prepare_dbos_logging()` runs before `DBOS(...)`.
- `apply_schedules` runs after `launch()` with one entry named `cairn-heartbeat`, context `"phase-0"`, cron from `CAIRN_HEARTBEAT_CRON`.
- The workflow returns `None` (design §8 sketched a dict return; DBOS types scheduled workflows as returning `None`).
- The liveness thread starts only after launch and `apply_schedules` succeed.

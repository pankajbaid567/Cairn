### Plain-PostgreSQL requirements, in short
For a CREATEROLE / CREATEDB / BYPASSRLS non-superuser to build the Cairn databases and extensions on plain PostgreSQL 18:
1. Roles: it creates them itself. It can change LOGIN, CREATEDB, CREATEROLE, INHERIT and the password afterwards, but not SUPERUSER or REPLICATION (and bootstrap does not name BYPASSRLS).
2. Databases: `GRANT <owner> TO <admin> WITH INHERIT FALSE, SET TRUE` for `cairn_owner` and `cairn_dbos`, then `CREATE DATABASE … OWNER <owner>`.
3. Privileges on those databases (`REVOKE`/`GRANT` of CONNECT and TEMPORARY, the `public` schema revoke): only under `SET ROLE <owner>`; run directly they do nothing and only warn.
4. The admin itself needs CONNECT on each database (granted under `SET ROLE <owner>` once PUBLIC lost it) and CREATE on the database while it creates an extension (granted, then revoked).
5. `vector` cannot be created by the admin on plain PostgreSQL, with or without `SET ROLE`. `btree_gist` can, with CREATE on the database. The only way for the admin to end up with `vector` is that it already exists in the database's template: `cairn-db emulate-managed-admin` creates both extensions in `template1` as the image superuser.
## Part 1b: the same sequence through the new code, on a throwaway server
Not on the core `db`: a separate container `cairn-fv4-e2e` (the same pinned image, port 55499 on 127.0.0.1, random passwords marked FAKE, removed with `--rm` afterwards) was used to run the real commands once before the unit tests were finished. Results:
- `cairn-db emulate-managed-admin` with `CAIRN_ENV=demo`: exit 1 `CAIRN_ENV must be local or ci`, nothing changed. With `CAIRN_ENV=ci`: `cairn_admin` created, `btree_gist` and `vector` in `template1`; again: role `updated`, same extensions.
- `cairn-db init` as `cairn_admin` with `CAIRN_DB_ADMIN_MODE=managed`, no flag: roles created with SCRAM verifiers, grants, both databases, extensions found in the template, baseline migration applied; the second run changed nothing (`database cairn: exists`, roles `updated`, `up to date at version 1`). Final `datacl`: `cairn` `{owner=CTc/owner, app=c/owner, admin=c/owner}`, `cairn_dbos` `{dbos=CTc/dbos, admin=c/dbos}`; `public` schema ACL without CREATE for PUBLIC; the admin holds a SET-only (inherit f) and an ADMIN membership on `cairn_owner` and `cairn_dbos`, and ADMIN on `cairn_app`.
- `--allow-plaintext-password`: exit 2 before connecting for sslmode `prefer`, for mode `auto` or `superuser`; with `managed` and `verify-full` against this non-TLS server the flag is accepted and the connection then fails (exit 1, `OperationalError`), as it must. Calling `bootstrap(…, allow_plaintext=True)` directly with those settings on the local server sent plaintext passwords (the server stores SCRAM hashes), after which `cairn_app` and `cairn_owner` could log in with them.
- A managed role with BYPASSRLS set by hand (`ALTER ROLE cairn_app BYPASSRLS` as `postgres`): `bootstrap failed: managed mode cannot clear role attributes: cairn_app has BYPASSRLS`, exit 1, nothing changed. `CAIRN_DB_ADMIN_MODE=superuser` as `cairn_admin`: refused (`needs a superuser`).
- `bootstrap_database` as `cairn_admin` with `template1` stripped of both extensions: `btree_gist` was created (owner `cairn_admin`), a second run was a no-op, the temporary CREATE grant was gone afterwards, and a database spec with `vector` failed with `InsufficientPrivilege` (42501) while still revoking the grant and resetting the role.

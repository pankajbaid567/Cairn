# FV7: Cloudflare Pages Functions, `_routes.json`, `_headers`, Direct Upload and secrets
Resolved from Cloudflare's documentation and the npm registry on 3 Nov 2026 (task 9.2). Content was rephrased for compliance with licensing restrictions. Requirements 17.4 to 17.10; design FT-15, FT-16 and §14. Nothing here was tried against a live Cloudflare account (FU3 and FU6 are user steps); the items marked **FU6** are the ones only a real deploy can confirm.
## Answers
| Question | Finding | Effect on the files | Source |
|---|---|---|---|
| Functions routing | Routes come from the file tree under `functions/`. A file named with two sets of brackets (`[[path]].ts`) matches any depth below its folder, so `functions/api/[[path]].ts` serves `/api/x`, `/api/x/y/z`. The matched segments arrive as an array in `context.params.path`. A single set of brackets matches one segment. Without a matching Function, the request falls back to a static asset | `functions/api/[[path]].ts` exports `onRequest`. The proxy reads the original URL from the request, not from `params`, so the query string and encoded segments are forwarded as received. `/api` itself (no trailing segment) is not matched by `[[path]]`; it would be served as a static asset (a 404 or the SPA fallback), and the proxy also answers 404 for it | [Routing](https://developers.cloudflare.com/pages/functions/routing/) |
| `_routes.json` | Once a project has Functions, every request invokes the Function unless `_routes.json` in the build output directory limits it. Fields: `version` (1), `include`, `exclude`; `exclude` wins over `include`; wildcards are accepted. Limits: at least one include rule, at most 100 rules in total, each rule at most 100 characters. Wrangler generates the file when it is absent, but a hand-written one in the build directory is used as is | `public/_routes.json` is `{"version": 1, "include": ["/api/*"], "exclude": []}`. Vite copies `public/` into `dist/`, which is the build output directory, so static requests stay free and unlimited and only `/api/*` spends the 100,000 daily Workers-plan requests | [Routing](https://developers.cloudflare.com/pages/functions/routing/), [Functions pricing](https://developers.cloudflare.com/pages/functions/pricing/) |
| What happens when the daily Function allowance runs out | On the Workers Free plan the project can fail open (static assets keep being served, Functions are bypassed) or fail closed (an error page). The setting is in the dashboard under the project's Settings, Runtime. The allowance resets at midnight UTC | **FU6** note for the runbook: leave the project on fail closed, so an exhausted allowance shows an error and never exposes a path without the proxy token. With fail open the browser would reach only static files (the API lives behind the Function), so either choice is safe; fail closed makes the cause visible | [Routing](https://developers.cloudflare.com/pages/functions/routing/), [Functions pricing](https://developers.cloudflare.com/pages/functions/pricing/) |
| `_headers` | A plain file named `_headers` (no extension) in the static asset directory. A block is a URL pattern line followed by indented `Name: value` lines. Rules apply to **static asset responses**, not to responses a Function returns. A request matching several patterns inherits every matching rule. At most 100 rules, 2,000 characters per line. A header repeated across matching rules is joined with a comma | `public/_headers`: `/*` with `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` (the nginx values), and `/assets/*` with `Cache-Control: public, max-age=31536000, immutable` (Vite writes hashed files to `/assets/`). Function responses carry whatever the API sends; the three security headers are not added to them. The API returns JSON and the proxy sets none of them, so nothing in the browser depends on it | [Headers](https://developers.cloudflare.com/pages/configuration/headers/) |
| `wrangler.toml` for Pages | Supported with Wrangler 3.45.0 or newer. Required keys: `name` (alphanumeric and dashes), `pages_build_output_dir` and `compatibility_date`. `[vars]` become plain-text environment variables on `context.env`. When the file has `pages_build_output_dir` it becomes the source of truth: its fields can be seen but not edited in the dashboard. Environment overrides use `[env.production]` and `[env.preview]`; if one non-inheritable key (such as `vars`) is overridden in an environment, all non-inheritable keys must be given there. A file without `pages_build_output_dir` is only used for local development, with a warning | `apps/web/wrangler.toml`: `name = "cairn"`, `pages_build_output_dir = "./dist"`, `compatibility_date = "2026-11-03"` (the date of this check; Wrangler has no "latest"), `[vars] API_ORIGIN = "https://cairn-api.onrender.com"`. No `[env.*]` sections, so preview and production share the value. The file holds no secret. `API_ORIGIN` is the only value the user edits (FU6); `CAIRN_PROXY_TOKEN` is not in the file | [Configuration](https://developers.cloudflare.com/pages/functions/wrangler-configuration/) |
| Direct Upload with Functions | `wrangler pages deploy <dir>` uploads the folder (zip files are not supported) and, if a `functions/` folder exists in the directory where the command runs, compiles and uploads it too. Drag and drop in the dashboard does not compile a `functions/` folder. Wrangler limits: 20,000 files, 25 MiB per file | The command runs from `apps/web` (where `functions/` and `wrangler.toml` live) with `dist` as the directory: `pnpm dlx wrangler@4.156.2 pages deploy dist`. Drag and drop must not be used. `make web-dist` builds `dist/` first | [Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/), [Limits](https://developers.cloudflare.com/pages/platform/limits/) |
| Creating the project | `wrangler pages project create` prompts for the project name and production branch and creates an empty project; later deploys reuse the values (cached in `node_modules/.cache/wrangler`). `wrangler pages deploy` can also create the project on first use | Runbook: `wrangler pages project create cairn --production-branch main` first, so the secret can be set before any deployment (next row) | [Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/), [Wrangler pages commands](https://developers.cloudflare.com/workers/wrangler/commands/pages/) |
| Pages secrets | `wrangler pages secret put <KEY> --project-name <name>` creates or updates an encrypted variable; it is readable only through `context.env`. Cloudflare states that secrets must be set **before a deployment that uses them**. The dashboard offers the same under Settings, Variables and Secrets (Encrypt). Local development reads `.dev.vars` or `.env` next to the Wrangler file | **Order change against design FU6**: create the project, then `secret put CAIRN_PROXY_TOKEN`, then deploy. Setting it after the first deploy also works but needs one more deploy to take effect, and until then `/api/*` answers 503 `proxy_not_configured`. `docs/deploy.md` (task 9.4) uses the create, secret, deploy order. `.dev.vars` (secrets for `wrangler pages dev`) is not matched by the repo's `.gitignore` (which has `.env` and `.env.*`), so the runbook tells the user not to create one in `apps/web`, and `test_pages_config.py` fails if `apps/web/.dev.vars` exists | [Bindings](https://developers.cloudflare.com/pages/functions/bindings/), [Wrangler pages commands](https://developers.cloudflare.com/workers/wrangler/commands/pages/) |
| Wrangler version to pin | npm registry `latest` for `wrangler` on 3 Nov 2026 is **4.156.2** (published 2 Nov 2026, requires Node 22 or newer; the Node 24 image is fine). `pages secret put`, `pages deploy` and `pages project create` exist in the 4.x command reference | `docs/deploy.md` pins `wrangler@4.156.2`. Not added to `apps/web/package.json`: the user runs it through `pnpm dlx`, so the web lockfile and the audit gate are unchanged | [npm registry](https://registry.npmjs.org/wrangler/latest), [Wrangler pages commands](https://developers.cloudflare.com/workers/wrangler/commands/pages/) |
| Origin timeout | A Pages Function is a Worker. Workers have **no wall-clock limit** on an HTTP request while the client stays connected, and **no set time limit on a single subrequest**. CPU time is limited (10 ms per request on Free) but time spent waiting on `fetch()` does not count. Cloudflare's proxy waits about 100 seconds (older pages) to 125 seconds (current Error 524 page) for an origin to answer when it is the proxy in front of an origin; that applies to proxied origins, and the page does not describe the Worker `fetch()` case | The proxy sets its own limit: `UPSTREAM_TIMEOUT_MS = 90_000` through an `AbortController`, covering the Render wake (about 60 s, FV6). It is under both 100 s figures, so the browser never meets a Cloudflare 524 first. The timer stops when the response headers arrive; a slow body is not cut. **FU6**: the first request after a sleep should be timed | [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Error 524](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/) |
| Free-plan Function limits | Workers Free: 100,000 requests per day (reset at midnight UTC, error 1027 beyond), 10 ms CPU per request, 128 MB memory, 50 subrequests per request, 6 simultaneous connections waiting for headers, request header size 128 KB, URL 16 KB, 64 variables of 5 KB each. Request body limit comes from the zone plan (100 MB on Free). Pages: 500 builds per month (not used with Direct Upload), 20,000 files, 25 MiB per file, 100 header rules | One subrequest per request, so the 50 limit is not reached. The proxy buffers request bodies only up to `MAX_BODY_BYTES = 1_048_576`, so memory stays far below 128 MB. The proxy does almost no CPU work, so 10 ms holds (**FU6** can confirm in the dashboard metrics). Response bodies stream | [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Pages limits](https://developers.cloudflare.com/pages/platform/limits/) |
## Differences from design §14
| Design says | Implementation does | Reason |
|---|---|---|
| `forwardHeaders(incoming, token)` | `forwardHeaders(incoming, token, host?)`; `content-length` is not copied | `x-forwarded-host` needs the request host and `Headers` does not reliably carry it. `fetch` computes the length of the buffered body itself, and a copied length that disagrees would be an error |
| The request body streams through | The body is read into memory up to 1 MiB, then sent | Enforces the 1 MiB limit for chunked requests that have no `Content-Length` (Requirement 17.9 names only the header; the extra check changes nothing for honest clients) and avoids the `duplex` option |
| Function sets the secret after the deploy (FU6 text) | Create the project, set the secret, then deploy | Cloudflare requires secrets before the deployment that uses them (row "Pages secrets") |
Nothing else differs.
## Not confirmed (user, FU6)
- That `wrangler pages deploy dist` run from `apps/web` picks up `functions/` together with `public/_routes.json` and does not regenerate `_routes.json`.
- Time of the first request after a Render sleep through the Function (target: under 90 s).
- The dashboard Runtime setting (fail open or closed) after the first deploy.

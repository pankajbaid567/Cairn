# FV5: DBOS 3.3.0 in one long-lived process (combined mode)
Resolved 2 Nov 2026 (task 5.1). Requirements 8.3, 8.4, 8.5 and 7.2; design FT-10, FT-12 and §7. Probe: [FV5-probe.py](FV5-probe.py), raw output in [FV5-probe.out](FV5-probe.out). It ran against a throwaway database `cairn_test_dbos_fv5_<hex>` on the core `db` (bootstrapped with `dbos_spec`, dropped at the end) and a scratch container `cairn-fv5-tls-<hex>` (the same pgvector image with `ssl=on` and a self-signed certificate, removed at the end). The live `cairn_dbos` database and the running `worker` were not touched. Versions: Python 3.12.12, DBOS 3.3.0, psycopg 3.3.6.

## Answers
| Question | Answer |
|---|---|
| Can `DBOS()` be constructed again after a failed launch in the same process? | **Yes, after `DBOS.destroy()`.** Three failed launches (closed port, wrong password, missing database) each followed by `destroy()`, then a good construct, launch and schedule in the same process: launched in 3.8 s (it includes DBOS's own migrations on the empty database; 2.8 s on an earlier run) and a `cairn-heartbeat` run succeeded. A failed launch raises `OperationalError` from `DBOS.launch()` within a few milliseconds (no SQLSTATE: the connection never reached the server's SQL layer or libpq reports none); the constructor itself does not connect. `destroy()` after a failed launch took under 10 ms and left no DBOS thread behind (0 non-main threads before, after each failure and after the good run). |
| Does a retry work without `destroy()`? | **No.** `DBOS()` returns the stale instance, and the second launch raised `OperationalError` again. After a `DBOS.destroy()` the next launch worked. So the runner always destroys before it retries. |
| Can DBOS launch from a non-main thread while uvicorn serves in the main thread? | **Yes.** `uvicorn.Server.run()` in the main thread, launch and `apply_schedules` in a background thread: launched in 0.6 s, a heartbeat run succeeded, `/healthz` answered 200 while DBOS was up, `destroy()` from that thread took 32 ms. DBOS installs no signal handler, so there was no "signal only works in main thread" error. The same holds for the real `python -m cairn_combined` (below). |
| `automatic_backfill` default | **False** in DBOS 3.3.0 (`schedule.get("automatic_backfill", False)` in `_sys_db.py`, `_dbos.py`; the database column defaults to `FALSE`). `apply_schedules` without the key stored `False`; with `True` it stored `True`. The code now sets `False` explicitly so a library default change cannot start replaying missed ticks. |
| Idle query rate against the system database | **About 9.5 transactions per second** on an otherwise idle DBOS database with one schedule (`0 */5 * * * *`), measured over 60 s after 15 s of settling: 570 transactions (per 10 s: 100, 100, 104, 96, 90, 80; an earlier run gave 568), 2,000 tuples returned, 5 idle connections (6 on the earlier run). The rate does not depend on the cron, so it is DBOS's own polling (scheduler, queue and notification threads). |
| TLS settings in the URL | **Work.** `sslmode=verify-full` with `sslrootcert=<cert path>` in `system_database_url` launched against a TLS server and `pg_stat_ssl` showed the DBOS session encrypted. A missing `sslrootcert` file failed the launch; `verify-full` with no `sslrootcert` (system roots) failed against the self-signed server, as expected. `sslmode=require` against the core `db` (ssl off) was refused, and `disable` connected, so the parameters reach libpq. The Neon handshake itself is proven only by FU2/FU3. |

## What this changed
- **Requirement 8.4 (give up after five failed attempts) is not implemented.** Its condition is "IF DBOS cannot be constructed again in the same process", and it can. The runner retries with backoff until launch works or `stop()` is called, as design Property 9 states. The design's error-handling row "DBOS relaunch not possible in process" does not apply.
- `schedule_spec` sets `automatic_backfill: False`.
- Every attempt calls `prepare_dbos_logging()` again, because `DBOS()` resets its logger each time.

## Consequence for Neon compute (FT-12), to carry into the deploy runbook
DBOS polls its database about 9 to 10 times a second whenever it is launched. Neon scales to zero after 5 minutes without activity, so while the Render service is awake Neon is awake too; Neon sleeps only after Render has slept (15 minutes without inbound traffic) and 5 more minutes have passed. Neon compute hours therefore track Render awake hours plus about 5 minutes per wake, not the traffic of the app. At 0.25 CU, 400 awake hours a month use the 100 CU-hours. FT-12's "no keep-alive pinger" still holds (a pinger would keep both awake permanently), but the figure "the heartbeat cron costs nothing" does not: the cron is free, the polling is not. Options for Phase 1 if the budget gets tight: DBOS polling intervals (`notification_listener_polling_interval_sec`, queue `polling_interval_sec`), or fewer DBOS features in the always-on process. Not changed here.

## Real process, for Requirement 8.2, 8.5 and 8.7
`python -m cairn_combined` against a throwaway DBOS database (`apps/combined/tests/integration`, also run by hand): `/healthz` 200 after 0.54 s, `/readyz` with `jobs` ok after 0.82 s, two `worker.heartbeat` lines in 12 s with cron `*/5 * * * * *`, SIGTERM to exit in 0.3 s (`jobs.stopped` logged). The exit status is -15 (SIGTERM) because uvicorn 0.54 re-raises the signal after a clean shutdown; a container reports 143. With a wrong DBOS password `/healthz` stays 200, `/readyz` is 503 with `jobs_not_launched` and an attempt count that grows, and SIGTERM still stops it in under 20 s.

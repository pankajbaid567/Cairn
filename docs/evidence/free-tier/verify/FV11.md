# FV11: `sslrootcert=system` with psycopg-binary 3.3.6 in `python:3.12.16-slim`

Resolved 2 Nov 2026 (task 4.1). Requirements 4.4 and 7.2; design FT-14 and §6. The question: does the libpq bundled with psycopg 3.3.6 (binary) accept `sslrootcert=system`, and does that value load a usable set of root certificates inside the runtime image (`python:3.12.16-slim@sha256:962f801b…d54e`, the base of `infra/docker/python-app.Dockerfile`)?

## Answer

`system` is accepted by libpq but loads no root certificates in the image. Every `verify-full` connection with `sslrootcert=system` fails with `certificate verify failed`, including against a server whose CA is in the image's Debian bundle. An explicit path to the Debian bundle, `sslrootcert=/etc/ssl/certs/ca-certificates.crt`, works with `verify-full`.

Decision recorded here: `.env.neon.example` keeps `CAIRN_DB_SSLMODE=verify-full` and sets `CAIRN_DB_SSLROOTCERT=/etc/ssl/certs/ca-certificates.crt` (changed in task 4.1). Task 9.1 must use the same value in `render.yaml` instead of `system`. The `require` fallback that design FT-14 names is not needed, and it would not fit OQ-1: `cairn-db init --allow-plaintext-password` is accepted only with `verify-full` (task 4.3), so `require` would make `make remote-init` exit 2.

## Facts

| Item | Value | How it was read |
|---|---|---|
| psycopg | 3.3.6, implementation `binary` | `psycopg.__version__`, `psycopg.pq.__impl__` on the host and in `cairn-python:local` |
| libpq | 180006 (18.0.6), the same at build and run time | `psycopg.pq.version()`, `psycopg.pq.__build_version__` |
| `sslrootcert=system` | Supported since libpq 16, so the keyword is accepted | the PostgreSQL 16 release notes and the libpq "SSL Support" page; confirmed by the probe below, which reaches certificate verification |
| OpenSSL that libpq links | `libssl-c64c0f6b.so.3` and `libcrypto-cff3d539.so.3` from `psycopg_binary.libs`, OpenSSL 3.5.8 (25 Aug 2026) | `ldd libpq-*.so.5.18` in the image; `OpenSSL_version()` through `ctypes` |
| Its compiled default store | `OPENSSLDIR: "/host/tmp/libpq.build"`, so `X509_get_default_cert_file()` is `/host/tmp/libpq.build/cert.pem` and the directory `/host/tmp/libpq.build/certs`; neither exists in the image | `OpenSSL_version(OPENSSL_DIR)`, `X509_get_default_cert_file()`, `X509_get_default_cert_dir()` through `ctypes` |
| Overrides OpenSSL honours | `SSL_CERT_FILE`, `SSL_CERT_DIR` | `X509_get_default_cert_file_env()`, `X509_get_default_cert_dir_env()` |
| CA bundle in the image | `ca-certificates 20250419+deb13u1`; `/etc/ssl/certs/ca-certificates.crt` exists (297 entries in `/etc/ssl/certs`); `/usr/lib/ssl/cert.pem` links to it, but that is the system OpenSSL's directory, not the bundled one's | `dpkg -l`, `ls` in the image |

The wheel also carries an OpenSSL 1.1.1k `libcrypto` (OPENSSLDIR `/etc/pki/tls`, also absent), pulled in by the Kerberos libraries; libpq's TLS does not use it.

## Probe

A throwaway server `cairn-fv11-pg` (the pinned `pgvector/pgvector:0.8.6-pg18` image, 256 MB limit, `ssl=on`, a server certificate for `localhost` signed by a scratch CA made with `openssl` for this probe only, two-day validity). The client ran in `cairn-python:local` in the server's network namespace (`--network container:cairn-fv11-pg`), with `SSL_CERT_FILE` and `SSL_CERT_DIR` unset unless the case says otherwise. The container, its anonymous data volume and the scratch keys were removed afterwards; no other container or volume was touched, and the core `db` was not used.

| Case | Scratch CA not trusted | Scratch CA appended to `/etc/ssl/certs/ca-certificates.crt` |
|---|---|---|
| `verify-full`, `sslrootcert=system` | refused: certificate verify failed | refused: certificate verify failed |
| `verify-full`, `sslrootcert=/etc/ssl/certs/ca-certificates.crt` | refused: certificate verify failed | connected, `ssl_in_use=True` |
| `verify-full`, `sslrootcert=system`, `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt` | refused: certificate verify failed | connected, `ssl_in_use=True` |
| `require` | connected, `ssl_in_use=True` | not run |
| `prefer` | connected, `ssl_in_use=True` | not run |

The second column is the deciding one: with the CA present in the Debian bundle, `system` still fails, and the explicit bundle path and `SSL_CERT_FILE` both succeed. So `system` reads only the non-existent `/host/tmp/libpq.build` store.

The probe client, for the record (the password is the scratch server's, used once):

```python
import os, sys, psycopg, psycopg.pq as pq
print("psycopg", psycopg.__version__, pq.__impl__, "libpq", pq.version())
os.environ.pop("SSL_CERT_FILE", None); os.environ.pop("SSL_CERT_DIR", None)

def attempt(label, **tls):
    try:
        with psycopg.connect(host="localhost", port=5432, dbname="postgres", user="postgres",
                             password="<scratch>", connect_timeout=5, **tls) as conn:
            print(f"{label}: connected ssl_in_use={conn.pgconn.ssl_in_use}")
    except psycopg.OperationalError as exc:
        print(f"{label}: refused ({str(exc).strip().splitlines()[-1][-120:]})")

# cases: sslmode verify-full with sslrootcert "system" or the bundle path; "system" with
# SSL_CERT_FILE set to the bundle; sslmode require; sslmode prefer
```

## Alternatives considered

| Option | Effect | Chosen |
|---|---|---|
| `CAIRN_DB_SSLROOTCERT=/etc/ssl/certs/ca-certificates.crt` with `verify-full` | Verifies Neon's certificate (Neon serves a publicly trusted certificate; FV0) against the image's Debian bundle. No image change; the value is visible in `.env.neon` and `render.yaml` | Yes |
| `ENV SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt` in the runtime stage and keep `system` | Also works (probe row 3), but hides the trust store in the Dockerfile and breaks silently if the variable is dropped | No; can be added later if wanted |
| `sslmode=require` (the FT-14 fallback) | Encrypts but does not verify the server, so a spoofed endpoint is not detected; and `--allow-plaintext-password` (OQ-1) refuses it | No |

Caveats: the path is the one in `python:3.12.16-slim` (Debian 13). On the macOS host, outside the image, the path does not exist; host-side tools keep the default `prefer` for the local `db`. `sslrootcert=system` also forces `verify-full` in libpq, so it never mixed with weaker modes anyway. Only FU2 (`make remote-init`, user-run) proves the Neon handshake itself.

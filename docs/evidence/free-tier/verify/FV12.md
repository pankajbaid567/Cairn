# FV12: S1 topic tokens under the `simple` text-search configuration

Resolved 2 Nov 2026 (task 3.1), before the S2 harness was changed. Requirement 3.3; design §5 and FT-05.

Question: do `to_tsvector('simple', …)` and `websearch_to_tsquery('simple', …)` give matching lexemes for the S1 topic tokens `t<cluster>_<j>`?

Server: `cairn-db-1`, `pgvector/pgvector:0.8.6-pg18@sha256:2ba9ca5f…7e7a`, `PostgreSQL 18.6 (Debian 18.6-1.pgdg12+2) on aarch64-unknown-linux-gnu`; `default_text_search_config` is `pg_catalog.english` (the harness always names `simple`). Run with `docker compose exec -T db psql -U postgres -At`.

## The two statements of the task

| Statement | Result |
|---|---|
| `select to_tsvector('simple', 't3_5 t3_6')` | `'5':2 '6':4 't3':1,3` |
| `select websearch_to_tsquery('simple', 't3_5 or t4_1')` | `'t3' <-> '5' \| 't4' <-> '1'` |
| `select to_tsvector('simple', 't3_5 t3_6') @@ websearch_to_tsquery('simple', 't3_5 or t4_1')` | `t` |
| `select to_tsvector('simple', 't3_6 t9_9') @@ websearch_to_tsquery('simple', 't3_5 or t4_1')` | `f` |

`ts_debug('simple', 't3_5')` shows why: the default parser reads `t3` as a `numword`, `_` as a blank and `5` as a `uint`, so each topic token becomes two lexemes at adjacent positions.

## Edge cases

| Statement | Result | Meaning |
|---|---|---|
| `to_tsvector('simple','t1_3 t3_1') @@ websearch_to_tsquery('simple','t3_3 or t13_1')` | `f` | No match across token boundaries: after a number lexeme the next lexeme is always `t<c>` or `w<nnnn>` |
| `to_tsvector('simple','t3_50 t13_5') @@ websearch_to_tsquery('simple','t3_5')` | `f` | `50` and `t13` are whole lexemes, so neither is a prefix match |
| a cluster-3 body (`w0012 t3_1 w0003 t3_0 w4999 t3_3 t3_2`) against `t3_0 or t3_1 or t3_2 or t3_3` | `t` | The S2 query shape |
| the same body with cluster 4 tokens against the cluster-3 query | `f` | |
| `to_tsvector('simple','w0012')` | `'w0012':1` | Filler tokens stay one lexeme |
| `ts_rank_cd(to_tsvector('simple','t3_5 t3_6 t3_5'), websearch_to_tsquery('simple','t3_5 or t4_1'))` | `0.2` | Ranking works on phrase queries |
| `websearch_to_tsquery('simple','t3_5 t4_1')` | `'t3' <-> '5' & 't4' <-> '1'` | Without `or` the terms are ANDed, so the harness joins with ` or ` |

## Answer

The lexemes do not match one-to-one: `simple` splits every topic token at `_`. They still match exactly the right documents, because `websearch_to_tsquery` turns each token into the phrase `'t<c>' <-> '<j>'`, and in an S1 body a `t<c>` lexeme followed directly by `<j>` only occurs inside the token `t<c>_<j>`. No change to the S1 generator or to the configuration is needed; the harness keeps `TS_CONFIG = "simple"` and joins the terms with ` or `.

Effect on plans: a GIN index stores lexemes without positions, so a phrase query is answered by the index as an AND of the lexemes (`t3` and `5`) and the heap scan rechecks the phrase. FTS plans therefore show a `Bitmap Heap Scan` with a `Recheck Cond` on `body_tsv` above the `Bitmap Index Scan` on `chunks_fts_idx`; `Rows Removed by Index Recheck` can be non-zero. The plan analyzer counts only `Rows Removed by Filter`, so the recheck does not change any reported field.

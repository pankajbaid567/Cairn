# FV6: Render free web service and the Blueprint

Resolved from Render's documentation on 3 Nov 2026 (task 9.1). Content was rephrased for compliance with licensing restrictions. Requirements 6.2, 17.1 and 17.2; design FT-10 to FT-12 and §14. Nothing here was tried on a live Render account (FU4 and FU5 are user steps); the items marked **FU5** are the ones only a real deploy can confirm.

## Answers

| Question | Finding | Effect on `render.yaml` | Source |
|---|---|---|---|
| HTTP health checks | Render probes each running web service every few seconds. With a path set, an instance is healthy when it answers 2xx or 3xx within 5 seconds. Unhealthy running instances are restarted. A new deploy goes live only when all new instances pass, and is cancelled if that does not happen within 15 minutes. The Host header is the `onrender.com` name (or a verified custom domain) | `healthCheckPath: /healthz`. It checks the process only (FT-11) and is exempt from the proxy token, so a Neon outage cannot cause a restart loop. The 5 s limit leaves no room for a database call | [Health checks](https://render.com/docs/health-checks) |
| Do health checks count as inbound traffic for the 15-minute sleep? | **Not stated.** The free-plan page defines the sleep trigger as 15 minutes without inbound traffic and names HTTP requests and WebSocket messages. The health-check page does not say whether its probes count. Search results for this question were forum and blog posts, not Render documentation, so no claim is made | None. FT-12 stays (no pinger). **FU5**: after the first deploy, leave the service untouched for about 20 minutes and check the dashboard for "spun down". If it never sleeps, health probes count, and Neon would then stay awake too (compare the 186 CU-hour estimate of FT-12); the remedy would be to drop `healthCheckPath`, which falls back to TCP checks, and accept that readiness is then judged by port only | [Deploy for Free](https://render.com/docs/free) |
| Free-plan sleep and wake | A free web service sleeps after 15 minutes without inbound traffic and wakes on the next HTTP request or WebSocket connection, which takes about one minute. The filesystem is ephemeral. 750 free instance hours per workspace per month; spun-down time costs none. Render may restart a free service at any time. Render may suspend a free service that starts an uncommonly high volume of outbound traffic, with an external database as an example | The Pages Function waits up to 90 s for the wake (task 9.2). The process keeps no local state. Heartbeats pause while asleep (FT-12) | [Deploy for Free](https://render.com/docs/free) |
| SIGTERM grace on deploy and on spin-down | On a deploy Render starts the new instance, shifts traffic, waits 60 seconds, then sends SIGTERM to the old process and SIGKILL after the shutdown delay. The delay defaults to 30 s and `maxShutdownDelaySeconds` (1 to 300) changes it. The deploy page describes SIGTERM for deploys and restarts; it does not describe the spin-down signal separately, so the same 30 s is assumed there | Not set. `cairn-combined` drains within 20 s (Requirement 8.7, `GRACEFUL_SHUTDOWN_S`), inside the 30 s default | [Deploys](https://render.com/docs/deploys), [Blueprint spec](https://render.com/docs/blueprint-spec) |
| Environment variables as Docker build arguments | For a Docker service Render passes the environment variables to the build as build arguments as well as to the container at run time. Render warns against referencing sensitive build arguments in the Dockerfile because they could land in the image | The shared Dockerfile declares only `ARG PACKAGE` (default `cairn-combined`) and no secret. `test_runtime_settings` asserts the Blueprint sets no variable named `PACKAGE`, so the default holds (Requirement 17.3) | [Docker on Render](https://render.com/docs/docker) |
| `dockerCommand` | Optional start command; without it Render uses the Dockerfile's `CMD`. Multiple commands need `/bin/sh -c`. The shared Dockerfile has no `CMD`, and its `PATH` starts with `/app/.venv/bin`, so a single program name resolves | `dockerCommand: cairn-combined` | [Docker on Render](https://render.com/docs/docker), [Blueprint spec](https://render.com/docs/blueprint-spec) |
| `dockerfilePath`, `dockerContext` | Both are relative to the repo root; the context defaults to the root | `./infra/docker/python-app.Dockerfile` and `.` (the Dockerfile copies from the root, and `.dockerignore` filters the context, which Render honours) | [Blueprint spec](https://render.com/docs/blueprint-spec), [Docker on Render](https://render.com/docs/docker) |
| `PORT` | A web service must bind `0.0.0.0` and Render forwards to one port. The default is 10000 and `PORT` can be overridden in the environment. Ports 18012, 18013 and 19099 are reserved. A different bound port is usually detected | `PORT` is not set. `cairn-combined` binds `0.0.0.0:${PORT:-10000}` (task 5.1). `test_runtime_settings` asserts the Blueprint does not set it | [Web services](https://render.com/docs/web-services) |
| `sync: false` | Marks a secret: Render asks for the value only when the Blueprint is first created; later Blueprint updates ignore these keys, so a key added afterwards must be entered by hand; preview environments omit them; not allowed in environment groups | Used for `CAIRN_DB_HOST`, `CAIRN_APP_DB_PASSWORD`, `CAIRN_DBOS_DB_PASSWORD`, `CAIRN_PROXY_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`. `docs/deploy.md` (task 9.4) must say that a key added to the Blueprint later needs a manual entry | [Blueprint spec](https://render.com/docs/blueprint-spec) |
| Region `singapore` on the free plan | `singapore` is one of five regions (oregon, ohio, virginia, frankfurt, singapore) and cannot change after creation. Neither the free-plan page nor the Blueprint spec limits free instances to particular regions | `region: singapore`, paired with Neon `aws-ap-southeast-1` (FV2, OQ-4). **FU4**: the dashboard would show the region as unavailable at creation if the free plan did not allow it | [Blueprint spec](https://render.com/docs/blueprint-spec), [Deploy for Free](https://render.com/docs/free) |
| Auto deploys | `autoDeploy` is deprecated; `autoDeployTrigger` takes `commit`, `checksPass` or `off` and wins if both are present | `autoDeployTrigger: "off"` instead of the design's `autoDeploy: false`. Quoted, because an unquoted `off` is a boolean in YAML 1.1. A test asserts the string. Deploys are manual (FU5) | [Blueprint spec](https://render.com/docs/blueprint-spec) |
| Free plan size | The `free` plan is 0.1 CPU and 512 MB | `plan: free`; matches the `freetier` profile limits (FT-17) | [Blueprint spec](https://render.com/docs/blueprint-spec) |

## Differences from design §14

| Design says | Blueprint does | Reason |
|---|---|---|
| `autoDeploy: false` | `autoDeployTrigger: "off"` | `autoDeploy` is deprecated (above) |
| Flow-style `envVars` entries | Block style, same keys and values | Readability, comments per entry; the parsed result is the same |

Nothing else differs. The values `CAIRN_DB_SSLMODE=verify-full` and `CAIRN_DB_SSLROOTCERT=/etc/ssl/certs/ca-certificates.crt` follow [FV11](FV11.md) and equal `.env.neon.example`; a test compares them.

## Checks run

- `uv run pytest tests/scripts/test_render_blueprint.py`: 11 passed (service shape, `sync: false` on every secret-like key with no value, no admin, owner, superuser, postgres or neon key, TLS values equal to `.env.neon.example`, no connection string or long hex literal).
- `CombinedSettings` loaded in a scratch process from the Blueprint's non-secret values plus dummy secrets: accepted (`env=demo`, `sslmode=verify-full`, port 10000, heartbeat `0 */5 * * * *`, timeout 5.0 s). No real value was used or printed.
- `make secrets` (gitleaks over the working tree): no leaks found.
